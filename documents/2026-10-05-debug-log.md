# 2026-10-05 디버깅 기록 — 비행 전환이 한 번도 일어나지 않던 이유

**한 줄**: 플래너가 비행 구간을 계획하지 못하던 원인은 **네 개**였고, 모두 제거한 뒤
`계획 → 전환점 → 변신 실행` 체인이 처음으로 끝까지 이어졌다.

이 문서는 세 가지를 적는다 — 무엇이 문제였나, 어떻게 풀었나, 무엇이 남았나.
**틀린 가설도 적는다.** 같은 길을 다시 걷지 않기 위해서다.

---

## 0. 세션 시작 시점의 증상

| 증상 | 당시 해석 |
|---|---|
| 로봇이 0.5 m 박스에 올라타 전복 | 플래너가 장애물 위로 경로를 낸다고 봄 |
| 코너 앞에서 수십 초 주저 | 공간이 좁다고 봄 |
| `/mode_switch_points` 가 항상 빈 배열 | 에너지 모델이 비행을 비싸게 본다고 봄 |
| 경로가 A → B → A 로 진동 | 로컬 코스트맵이 멀리를 기억 못 한다고 봄 |

**네 해석이 전부 틀렸다.** 아래가 실제 원인이다.

## 1. 해결한 문제

### 1-1. BT 가 계획 실패마다 글로벌 코스트맵을 통째로 지웠다 — 가장 큰 건

**증상**: 경로가 A → B → A 로 진동. 막힌 걸 확인한 자리로 다시 돌아간다.

**원인**: `navigate_with_replanning.xml` 의 `ComputePathToPose` 복구 분기에
`ClearEntireCostmap(global)` 이 남아 있었다. 계획이 실패할 때마다(2 Hz) 학습한
장애물이 전부 사라졌다.

같은 파일 36 행 주석이 **이 루프를 정확히 경고하고 있었다**:

> 여기서 글로벌을 지우면 그 학습이 통째로 사라진다. 그러면 플래너가 다시 빈 벌판에
> 직선을 긋고, 로봇은 같은 벽에 코를 박고, 또 실패하고, 또 지운다 — 영원히 같은 실수를
> 반복한다

바깥 `RecoveryActions` 에서는 제거했는데 **안쪽 것은 남아 있었다.**

**측정** (9 초 간격 두 덤프):

```
금지(occ>=99) -> 자유 로 내려간 칸   1,721
LETHAL                              1,001 -> 466  (-535)
지워진 범위   x -0.30~6.15,  y -0.25~11.25   (맵 전체)
```

`raytrace_max_range` 가 3.0 m 이므로 센서 clearing 으로는 로봇에서 10 m 떨어진
벽을 지울 수 없다. **통째 삭제였다는 증거다.**

**수정**: 글로벌 clear 를 제거하고 `Wait 1.0` + 재계획으로 바꿨다. 로컬 clear 는
남겼다 — 로컬은 매 주기 재생성되므로 지워도 안전하다.

**검증**:

```
지워진 칸   1,721 -> 0
학습한 칸     286 -> 673      (단조 증가)
LETHAL      -535 -> +69
```

### 1-2. 미관측 영역이 자유공간이라 지상 경로가 늘 존재했다

**증상**: 지상 통과가 물리적으로 불가능한 월드에서도 `switch_points` 가 비었다.

**원인**: 두 설정이 겹친다.

```yaml
global_costmap:
  plugins: ["obstacle_layer", "elevation_layer", "inflation_layer"]   # static_layer 없음
  track_unknown_space: false                                          # 미관측 = 자유공간
```

```cpp
// state_space.cpp
bool LayerTerrainSource::roverTraversable(unsigned int mx, unsigned int my) const {
  const unsigned char g = grade_->getCost(mx, my);
  if (g == NO_INFORMATION) {return true;}   // 미관측 — 낙관
  return g <= cfg_.rover_max;
}
```

사전 지도가 없어 글로벌 코스트맵은 **센서로 본 것만** 담는다. 그런데 안 본 곳이
자유공간이고, 플래너도 미관측을 주행 가능으로 낙관한다.

**측정**:

```
높이 관측률          11,440 / 240,000 = 4.8%
master LETHAL 2,075 칸 중 높이 미관측   2,052 (98.9%)
nogap 월드(지상 통과 불가)의 박스 영역   100% 미관측
```

→ 플래너에게는 **항상 공짜 지상 경로가 있다.** 비행을 고를 이유가 생기지 않는다.

**수정**: `ElevationLayer::loadPriorMap()` — 벤치마크 맵의 정답 높이맵을 시작 시
`cells_` 에 심는다. 센서는 그 위에 덧씌우므로 동적 장애물 대응은 그대로다.
`use_prior_map:=true` 로 켠다 (기본 `false`).

이 연구는 '맵이 주어진 조건에서의 에너지 인식 경로 계획'이지 탐색/SLAM 이 주제가
아니므로, 전제에도 맞다.

### 1-3. prior map 을 심으면 장애물 둘레에 flyover 링이 생겼다

**증상**: prior map 을 켜면 `"해 없음, 425 노드 확장"`.

**원인**: `classify()` 3 번 분기.

```cpp
if (h <= rover_traversable_max_) {          // 이 칸 자체는 평평한 바닥 (<= 0.15 m)
  const double slope = localSlopeDeg(mx, my);   // 3x3 이웃에 평면 피팅
  const double step  = maxStepHeight(mx, my);   // 이웃과의 최대 고도차
  if (slope > 15° || rough > 0.03 || step > 0.05) {
    return flyover_or_block();              // -> flyover(200) 로 승격
  }
```

0.5 m 박스 **옆의 평평한 바닥 칸**을 보면:

- 자기 높이 `h` = 0.0 (바닥)
- 이웃에 박스가 있어 `step` = 0.5 m > 0.05 → 조건 통과
- 평면 피팅이 불연속을 가로질러 `slope` 도 15° 를 넘음

→ 바닥인데 flyover 로 찍힌다. 모든 장애물 둘레에 200 링이 생기고, prior map 으로
전 영역에 높이를 심으면 링이 맵 전체 장애물을 감싸 통로를 막는다.

**물리적으로 틀린 판정이다.** 바닥 옆에 턱이 있다고 그 바닥을 못 밟는 것이 아니다.
턱 자체가 장애물이고, 접근 여유는 `inflation_layer` 가 담당한다.

**수정**: `localSlopeDeg` / `maxStepHeight` 에서 **자기 높이가 `rover_traversable_max_`
를 넘는 이웃을 제외한다.**

```cpp
// 장애물 이웃은 '지형'이 아니다 — 자기 칸으로 따로 판정된다
if (o.mean() > rover_traversable_max_) {continue;}
```

양쪽 다 낮은 진짜 험지(0.08 m 차이)는 여전히 걸린다 — 두 칸 모두 한계 이하이기 때문.

### 1-4. (회귀) stash 에서 옛 런치 파일을 통째로 가져와 렌더 엔진 수정이 사라졌다

**증상**: prior map 을 켜자 카메라 화면이 깨지고, 로봇 둘레에 반경 0.5 m 원이 생기고,
지도가 엉뚱한 세로 막대로 나왔다.

**원인**: `git checkout stash@{0} -- navigation.launch.py` 로 가져온 버전이 더 오래된
베이스였다. HEAD 에 있던 `with_render_engine()` 이 통째로 빠져 있었고, 월드 SDF 에
박힌 `ogre`(v1) 가 그대로 쓰였다.

HEAD 주석이 그 결과를 적어두고 있었다:

> ogre v1 에서는 gpu_lidar 가 모든 빔에 range_min(0.5 m) 을 낸다. LiDAR 가 죽으면
> SLAM·obstacle_layer·elevation_layer 가 로봇 둘레 0.5 m 에 가짜 벽을 그린다.

세 증상이 전부 이 하나로 설명된다.

**수정**: prior map 추가분(`use_prior_map` 인자 + `RewrittenYaml`)만 **HEAD 위에**
다시 얹었다. `with_render_engine` 유지.

**교훈**: stash 에서 파일을 통째로 가져올 때는 **그 안에 의도한 것 말고 뭐가 더/덜
들어 있는지 먼저 diff 할 것.** params 는 덮일까 봐 제외했으면서 launch 는 그냥
가져온 것이 실수였다.

### 1-5. 전복의 직접 원인은 플래너가 아니라 컨트롤러였다

**측정**:

```
로봇이 올라타 전복된 칸 (3.775, 4.025) 의 측정 높이   0.564 m
ElevationLayer 분류                                  flyover(200)  — 정확
플래너 경로 157 점 중  flyover 0 개, 벽(254) 0 개      — 피해 갔다
```

**플래너는 피했는데 DWB 가 밟았다.** DWB 는 모드 개념이 없어 금지선이
`INSCRIBED(253)` 하나뿐이고, 200 은 '조금 비싼 바닥'일 뿐이다.
`ObstacleFootprint.scale` 을 0.02 로 낮춰 둔 탓에 그 통행료마저 거의 0 이었다.

**수정**: **로컬만** `fly_over: 254`, 글로벌은 200 유지.

- 글로벌 200 — 플래너가 `collides()=false, roverTraversable()=false` 로 읽어 AIR
  모드를 고를 수 있다. 254 면 AIR 가 탐색에서 배제되어 전환점이 영원히 안 생긴다
- 로컬 254 — 컨트롤러가 못 들어간다. **그 멈추는 자리가 곧 이륙 지점이다**

이 비대칭은 의도된 것이다.

### 1-6. 변신 모션 구현

`drobot_controller/transform_manager` — 암 4 개에 `cmd_pos` 를 **동시에** 쏘고
`/joint_states` 로 완료를 기다린다. 서비스 `/transform_to_drone`, `/transform_to_rover`.

쉘에서 `ros2 topic pub` 을 4 번 돌리면 매번 노드를 새로 띄우고 상대를 발견하느라
1~2 초씩 걸려 **암이 차례차례 올라갔다** (실측). 퍼블리셔를 들고 있는 노드 하나가
한 번에 쏘면 그 지연이 없다.

`drobot_controller/mode_switch_executor` — `/mode_switch_points` 를 구독해 로봇이
전환점 반경(0.9 m) 안에 들어오면 해당 변신 서비스를 호출한다.

설계 선택:
- 거리 비교는 **TF(`map` → `base_footprint`)** 로 한다. 전환점은 map 프레임,
  `/odom` 은 odom 프레임이라 그대로 비교하면 EKF 보정분만큼 틀린다
- `cmd_vel` 을 건드리지 않는다. 멈춤은 Nav2 의 일이고 여기서 손대면 컨트롤러와 싸운다
- 구독 QoS 는 `transient_local` (플래너가 그렇게 퍼블리시한다). 노드가 늦게 떠도
  마지막 계획을 받는다
- 재계획으로 같은 전환점이 다시 와도 `(pair_id, switch_type)` 으로 한 번만 실행하고,
  경로가 바뀌면 기록을 비운다

## 3. 틀린 가설 — 다시 밟지 말 것

측정으로 반증된 것들이다. 전부 그럴듯했고 전부 틀렸다.

| 가설 | 왜 틀렸나 |
|---|---|
| **경로가 flyover 를 관통한다** | 의심 지점 7 개의 실제 측정 높이가 **0.072 m**. flyover 가 아니라 inflation 이었다. `/global_costmap/costmap` 은 raw cost 가 아니라 OccupancyGrid(0~100)라 **occ 77 = raw 198/199/200** 셋 다에 대응한다 |
| **EKF 지연으로 TF 가 밀려 제어가 안 된다** | `/odom` 이 `/cmd_vel` 을 거의 정확히 추종했다 (cmd 0.060 / odom 0.061). 시스템은 로봇을 제대로 보고 있었다. EKF 가 50 Hz 를 못 맞추는 건 사실이나 원인이 아니었다 |
| **flyover 254 의 inflation 이 통로를 막는다** | `fly_over: 253`(inflation 안 생김)으로 바꿔도 **같은 자리에서 같은 식으로** 교착했다 |
| **공간이 좁아서 코너를 못 돈다** | 통과 가능 폭 **1.25 m** (로봇 폭 0.379 m). 그리고 Spin(공간 무관)도 실패했다 |
| **로컬 코스트맵이 멀리를 기억 못 해 경로가 바뀐다** | 경로는 전적으로 **글로벌**이 만든다. 로컬은 궤적만 고른다 |
| **에너지 파라미터 때문에 비행이 안 선택된다** | 에너지를 40 분의 1 로 줄여도 손익분기가 3.5 → 2.7 m 로 거의 안 움직였다. 실제 장벽은 전환 **시간**(9 초 × w_time 0.3 = 지상 2.16 m 어치)이었고, 더 근본적으로는 미관측 때문에 비교 자체가 성립하지 않았다 |

**방법론 교훈**: 이 세션에서 가장 비쌌던 실수는 **코스트맵 덤프의 형식을 잘못 읽은
것**이었다. `occ 100` 을 "최댓값 100 = 벽 없음"으로 읽어 "치명 셀 0 개"라는 정반대
결론을 냈다. 실제로는 Nav2 의 `cost_translation_table` 이 254 → 100 으로 압축한
것이었다. 숫자를 보기 전에 **그 숫자의 단위부터 확인할 것.**

## 4. 남은 문제

| 문제 | 아는 것 | 다음 단계 |
|---|---|---|
| **코너에서 간헐적 교착** | `fly_over` 200 / 253 / 254 **전부에서** 발생. 공간 부족·가짜 장애물·TF 지연 모두 아님. 로그는 `"No valid trajectories out of 819"` | FollowPath 에 `publish_evaluation: true` 를 켜고 `/evaluation` 에서 어떤 critic 이 궤적을 떨어뜨리는지 직접 볼 것 |
| **착륙 지점이 장애물 끝보다 1.8 m 뒤** | 박스는 y 7.0 에서 끝나는데 착륙이 y 8.775 | `landableAt` 의 관측 조건이 inflation 때문에 밀린 것으로 추정. 미확인 |
| **에너지 파라미터가 임의값** | `default` 는 `hover_power`(50 W)와 **72 배** 어긋난다 (takeoff 5.0 Wh vs 50W×5s=0.069 Wh). `derived` 도 측정값이 아니다 | 물리 유도(운동량 이론) 또는 **민감도 분석** — "비행이 이기는 조건을 비율의 함수로" 제시하면 측정 없이도 결과가 된다 |
| **`fly_over: 253` 은 쓰면 안 된다** | `updateCosts` 의 비용 하향 분기가 `cost_flyover_ = 200` 을 전제로 쓰여 있어, 253 이면 벽의 254 를 253 으로 끌어내린다. inflation 이 사라져 로봇이 벽에 박는다 (실측: y 3.956 진입, 벽이 y 3.95) | 쓰려면 그 분기의 임계값을 `cost_flyover_` 와 분리해야 한다 |
| **변신이 목표 각도에 못 간다** | 잔차 0.15~0.30 rad. 암 조인트 `friction` 5.0(앞)/3.0(뒤) 과 P 게인 20 의 평형점 `friction/20` = 0.25/0.15 rad 과 일치 (rr 실측 0.149 vs 예측 0.15) | 게인 상향은 시뮬을 불안정하게 만들어 되돌렸다. **마찰 값** 쪽을 볼 것 (5.0 N·m 는 소형 암에 비현실적) |
| **'비행을 선택하는가' 미검증** | `nogap` 은 지상 경로가 없어 비행이 **강제**다. 선택의 증거가 못 된다 | `base_map_h0.5_narrow`(틈 0.70 m)에서 "지상도 가능한데 비행을 고르는가"를 볼 것. **이게 연구 결과가 되는 쪽이다** |
| **실제 비행 없음** | 추력 물리가 양쪽 repo 어디에도 없다. `drobot.urdf.xacro` 링크 16 개에 rotor/prop 이 없고 `gazebo.xacro` 에 추력 플러그인도 없다 | 비행 담당자 범위. Gazebo Harmonic 내장 `MulticopterMotorModel` + `MulticopterVelocityControl` 이면 PX4 없이 가능 (px4_msgs 빌드 OOM 회피) |
| **바닥 노이즈** | 관측된 바닥 높이가 0.00 이 아니라 0.04~0.08 m 로 일정하게 깔린다 (최빈값 0.05~0.06) | 한계 0.15 m 아래라 당장 문제는 아니나 마진의 1/3 을 먹는다 |
| **`ElevationCell` 이 `max_z` 만 누적한다** | 나쁜 프레임 한 장이 그 칸에 영구히 남는다. 감쇠도 최소 관측 횟수 조건도 없다 | 최근 N 프레임 기반 또는 `count` 임계값. 센서 노이즈로 생기는 가짜 장애물의 구조적 원인 |

### 측정에 쓴 명령

```bash
# 코스트맵 / 높이맵 덤프
ros2 topic echo /global_costmap/costmap --once --full-length > dumps/cm.txt
ros2 topic echo /global_costmap/elevation_layer/elevation_grid --once --full-length > dumps/elev.txt
ros2 topic echo /plan --once --full-length > dumps/plan.txt
ros2 topic echo /mode_switch_points --once --full-length > dumps/sw.txt

# 주행 전체 기록 (코너 교착 추적용)
ros2 bag record -o dumps/bag_$(date +%H%M) /cmd_vel /odom /tf /tf_static /rosout

# 런치 로그 보존 — 화면에만 나오는 print 를 잡으려면 필수
ros2 launch ... 2>&1 | tee dumps/launch.log
```

**주의**: `/global_costmap/costmap` 은 `nav_msgs/OccupancyGrid` 이고 값이 0~100 으로
압축되어 있다. 변환은 Nav2 의 `cost_translation_table`:

```
raw 0   -> occ   0        raw 253 -> occ  99
raw 254 -> occ 100        raw 255 -> occ  -1
raw i (1~252) -> occ 1 + (97 * (i-1)) / 251      # 200 -> 77
```

occ 77 은 raw 198 / 199 / 200 셋 다에 대응하므로 **flyover 와 inflation 을 구분할 수
없다.** 구분이 필요하면 `elevation_grid`(실제 높이)를 같이 봐야 한다.
