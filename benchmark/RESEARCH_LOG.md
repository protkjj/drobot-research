# 연구일지 — 하이브리드 경로계획: A* vs RRT*, 우리 문제에서 어느 쪽인가

**작성 2026-08-23 · drobot-research · GPS-Denied 실내 드론-로버 하이브리드**

---

## 1. 왜 이걸 먼저 했나

`drobot_hybrid_planner` 패키지 이름이 `hybrid_rrt_star_planner`로 정해져 있었다.
그런데 **RRT\*를 고른 근거가 저장소 어디에도 없었다.** 경로계획의 표준은 A\*이고,
심사에서 "왜 굳이 RRT\*냐"는 질문은 반드시 나온다.

그래서 구현에 들어가기 전에 두 알고리즘을 실제로 비교하기로 했다.
전제는 하나였다 — **결과가 어느 쪽으로 나오든 그대로 보고한다.**
RRT\*를 정해놓고 뒷받침 숫자만 찾으면 나중에 더 아프게 돌아온다.

---

## 2. 실험 설계

ROS2/Gazebo 없이 **Python 독립 벤치마크**로 구성했다. 물리 시뮬레이션은
알고리즘 비교에 불필요하고, 결정론적이라 재현이 보장되며, macOS에서 바로 돈다.

| 항목 | 내용 |
|---|---|
| 상태공간 | 3D `(x, y, mode)` / 4D `(x, y, z, mode)` 양쪽 |
| 비용함수 | `C = α·E_motion + β·E_switch + γ·T` — kj의 `energy_params.yaml` 직접 로드 |
| 맵 | {easy, medium, hard} × {open, corridor} 6종, 20×14m ~ 24×16m |
| 시간 제약 | 2.0초 (`hybrid_rrt_params.yaml`의 `timeout`) |
| 비교 대상 | Dijkstra(참조 최적해) / A\* / Informed RRT\* |

**공정성 원칙**: 비용 계산은 `cost/energy.py` 한 곳에만 두고 세 플래너가 공유한다.
플래너마다 다른 비용 함수를 쓰면 성능 차이가 알고리즘 때문인지 문제 정의 때문인지
구분할 수 없게 된다.

목적이 중간에 "A\* 채택 근거 확보"로 바뀐 뒤에도 이 원칙은 유지했다.
오히려 RRT\*를 **더 강하게** 만들었다 — Informed 샘플링, k-nearest rewire,
공간 해싱, 시드 20개. 약한 상대를 이기면 아무도 믿지 않기 때문이다.

## 3. 결과

### 3-1. 현재 config에서는 A\*가 우위 (5/5)

2초 예산, 시드 20개.

| 맵 | A\* | A\*시간 | RRT\* 평균 | RRT\* σ | A\* 우위 |
|---|---|---|---|---|---|
| easy_open | **44.276** | 0.12s | 44.278 | 0.250 | +0.00% |
| easy_corridor | **47.744** | 0.12s | 48.473 | 0.305 | +1.53% |
| medium_open | **72.088** | 0.81s | 74.158 | 0.552 | +2.87% |
| medium_corridor | **79.256** | 0.95s | 79.502 | 0.627 | +0.31% |
| hard_open | **79.407** | 1.00s | 81.671 | 0.726 | +2.85% |

A\*는 0.12~1.00초에 **최적해**를 낸다 (Dijkstra 전수탐색과 비용 일치를 검증).
RRT\*는 같은 시간에 근사해이고, 실행할 때마다 다르다 (σ = 0.25~0.73).

### 3-2. 그런데 비행이 활발해지면 역전된다

`takeoff` 에너지를 낮춰 비행 유인을 키우면서 재측정했다.

| takeoff | A\* 모드전환 | A\* 우위 맵수 |
|---|---|---|
| 0.1 Wh | 1.33회 | 2/3 |
| 0.3 Wh | 1.33회 | **1/3** |
| 0.7 Wh | 1.33회 | **1/3** |
| 1.5 Wh | 1.33회 | **1/3** |
| 3.0 Wh | 0.67회 | 2/3 |
| **5.0 Wh (현재 config)** | **0회** | **3/3** |

`medium_open` 기준으로 보면 패턴이 명확하다.

```
takeoff 0.1~3.0  (비행 2회)  →  RRT*가 2.95~3.18% 우위
takeoff 5.0      (비행 0회)  →  A*가 2.74% 우위
```

**즉 3-1의 "A\* 5/5 승"은 현재 config가 비행을 구조적으로 배제한 결과였다.**
그 조건에서는 사실상 2D 지상 경로계획 문제이고, 거기서는 A\*가 강하다.

### 3-3. A\*의 열세는 격자 해상도 탓 — 하지만 대가가 있다

원인을 "A\*의 이/착륙 지점이 셀 중심(10cm)에 묶여서"로 보고 검증했다.

```
medium_open (takeoff 0.3Wh, 비행 2회)
  격자 0.20m  →  A* -4.56%   시간 0.20s
  격자 0.10m  →  A* -3.09%   시간 0.92s
  격자 0.05m  →  A* -0.50%   시간 3.40s  ← 2초 초과

hard_open
  격자 0.20m  →  A* -2.19%   시간 0.23s
  격자 0.10m  →  A* -0.31%   시간 0.97s
  격자 0.05m  →  A* +1.44%   시간 4.52s  ← 2초 초과, A*가 이김
```

가설이 맞았다. 해상도를 높이면 A\*가 따라잡고 추월한다.
**그러나 A\*가 이기는 해상도(5cm)에서는 운용 제약 2초를 위반한다.**

### 3-4. 4D에서는 A\*를 쓸 수 없다

고도 `z`를 최적화 변수로 올리면 상태공간이 25만~277만 노드로 커진다.
양쪽 모두 2초로 묶고 재면:

| 맵 | A\* (모든 z해상도) | RRT\* |
|---|---|---|
| easy_open | 44.276 | **44.050** |
| medium_open | **timeout** | 73.017 |
| medium_corridor | **timeout** | 78.102 |
| hard_open | **timeout** | 81.228 |
| hard_corridor | **timeout** | 해 없음 |

가장 거친 z해상도(0.5m)에서도 A\*는 3.75~4.97초가 걸린다.

다만 4D가 필요한 경우가 실제로 있다:

| 맵 | 3D | 4D | |
|---|---|---|---|
| medium_open | 72.088 | 69.750 | 3.24% 개선 |
| hard_open | 79.407 | 77.253 | 2.71% 개선 |
| **hard_corridor** | **해 없음** | 80.868 | **3D로는 못 푸는 문제** |

3D는 비행 고도가 `장애물높이 + 0.8m`로 고정이라, 천장(2.5m) 제약 하에서
**0.95m 넘는 장애물을 비행으로 넘지 못한다.** 4D는 1.55m까지 넘는다.

## 4. 결론

### 우리 상황에서는 A\* — 단, 조건부다

```
현재 설계 (3D, state_space_dimension: 3)
  → A* 채택.  0.12~1.00초에 최적해, 결정론적, 2초 제약 충족

비행이 활발해지는 조건 (takeoff 실측값이 낮게 나올 경우)
  → RRT*가 해 품질 1~3% 우위. 다만 A*는 격자를 촘촘히 하면 따라잡음
    (그 대가로 3.4~4.5초 소요 → 제약 위반)

4D로 확장할 경우
  → A* 사용 불가 (전부 timeout). RRT* 또는 다른 접근 필요
```

### A\*를 택하는 실질적 이유는 해 품질이 아니다

측정된 비용 차이는 **1~3%**다. 그런데 이 연구의 에너지 모델은 아직 실측 전이고,
`takeoff_energy = 5.0 Wh`는 같은 config의 `hover_power = 50W`로 계산한 값
(50W × 5s = 0.069 Wh)의 **72배**다. 파라미터가 수십 배 불확실한 상태에서
3% 최적화 차이를 근거로 알고리즘을 고르는 건 설득력이 약하다.

**A\*를 택하는 진짜 이유는 이쪽이다:**

| 이유 | 근거 |
|---|---|
| 최적성 보장 | Dijkstra 전수탐색과 비용 완전 일치 검증 |
| 결정론적 재현성 | σ=0. RRT\*는 σ=0.25~0.73으로 매 실행 다른 경로 |
| 시간 여유 | 0.12~1.00초 vs 제약 2.0초 (2~16배 여유) |
| 튜닝 부담 | 휴리스틱 하나. RRT\*는 goal_bias, gamma_rrt, step_size 등 다수 |

로봇 시스템에서 "같은 상황에 항상 같은 경로"는 디버깅·재현·인증에서 큰 가치가 있다.
"어제는 됐는데 오늘은 안 되네"의 원인을 하나 줄인다.

### 실무 권고

1. `drobot_hybrid_planner`의 클래스명을 `hybrid_rrt_star_planner` →
   **`hybrid_astar_planner`** 로 변경. 헤더가 아직 6줄뿐이라 지금이 바꾸기 쉽다.
2. Nav2의 `SmacPlanner2D`가 이미 A\* 계열이다. 처음부터 만들지 말고 구조를 참고할 것.
3. 단 **하이브리드(모드 전환)는 직접 구현해야 한다.** 표준 Nav2 플래너에는
   ground/air 상태 개념이 없다. `benchmark/planners/state_space.py`의
   전이 정의(이/착륙을 엣지로 표현)를 C++로 옮기면 된다.
4. **Phase 2에서 `takeoff_energy`/`landing_energy`를 최우선으로 실측할 것.**
   이 값이 알고리즘 선택보다 결과에 훨씬 큰 영향을 준다.

## 5. 이 결론을 신뢰할 수 있는 이유 — 발견한 버그 5개

실험 과정에서 내 구현의 버그를 5개 고쳤고, **각각이 결론을 뒤집을 수 있었다.**

| # | 버그 | 증상 | 영향 |
|---|---|---|---|
| 1 | A\* corner-cutting | 대각 이동이 벽 모서리를 관통. 높이 1.10m 벽을 통과하는 경로를 "최적해"로 냄 | A\*에 부당하게 유리 |
| 2 | 격자 각도 페널티 | A\*만 45° 배수로 제한되고 RRT\*는 연속 | **RRT\*가 5.3% 앞서 보임 — 결론 정반대** |
| 3 | RRT\* O(n²) | rewire 반경 하한이 반경 축소 성질을 파괴 | 4만 샘플에 34초 → k-nearest로 40배 가속 |
| 4 | RRT\* 착륙 노드 미생성 | 비행 후 지상 복귀 불가 (이륙 1, 착륙 0). 하이브리드 문제 0% 성공 | RRT\*에 부당하게 불리 |
| 5 | 상승각의 z해상도 종속 | `diz ∈ {-1,0,1}` 고정 → z=0.10에서 45°, z=0.05에서 26.6° | 해상도 높일수록 해가 나빠지는 비단조 |

2번을 안 고쳤으면 "RRT\*가 낫다"로 결론냈을 것이고,
4번을 안 고쳤으면 "RRT\*는 하이브리드 문제를 못 푼다"는 틀린 주장을 했을 것이다.

**"A\*가 이겼다"는 결과는 이 5개를 다 고쳐 공정한 조건을 만든 뒤에도 유지된 것**이다.
그게 이 결론을 신뢰할 수 있는 근거다.

## 6. 한계와 남은 일

**측정하지 못한 것**
- 실제 ROS2/Nav2 환경에서의 성능. 전부 Python 독립 실행이다.
- 동적 장애물, 재계획(replanning) 상황. 정적 맵 1회 계획만 측정했다.
- 실측 에너지 파라미터. 전부 `energy_params.yaml`의 추정값 기반이다.

**가설이 기각된 것 (정직하게 기록)**
- "좁은 통로에서 샘플링 기반이 실패한다" → **성립하지 않았다.**
  통로를 0.4m까지 좁혀도 RRT\*가 20/20 성공했다.
  `hard_corridor`에서 RRT\*가 실패한 건 통로가 좁아서가 아니라
  모드 전환 시퀀스가 필요해서였고, 그마저 버그 4를 고친 뒤 대부분 해소됐다.
