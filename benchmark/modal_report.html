장애물을 넘는 세 가지 방법

맵을 전부 안다는 가정에서 우회·밟고넘기·비행 세 modal 각각의 경로를 만들고, 같은 에너지 모델로 평가했다. 결론보다 먼저 나온 것은 결함 세 개였다 — 비용함수, 스무딩, 그리고 C++ 플래너가 아예 날지 못하던 문제.

계획 횟수 990 (가중치) + 90 (등반계수) 맵 5개 · 격자 0.1 m 플래너 A* (3D 상태공간)

01세 modal 의 정의

modal 을 가르는 것은 이동 수단이 아니라 장애물을 만났을 때의 선택이다.

우회 rover_detour O—— 0.15 m
밟고넘기 rover_climb OO— 0.70 m

밟고넘기와 하이브리드는 각각 우회의 상위집합이다 — 밟거나 날 수 있는 로봇은 그냥 도는 경로도 갈 수 있다. 따라서 두 modal 의 최적 비용은 우회보다 클 수 없다. 이 성질이 아래에서 결과 검증의 불변식으로 쓰인다.

02결함 1 — 전환 에너지가 40배 싸게 계상되고 있었다

비용함수의 두 에너지 항이 서로 다른 참조값으로 나눠지고 있었다.

이전 식 C = wE·E_motion/E_ref + wS·E_switch/E_switch_ref + wT·T/T_ref
↑ 0.5 Wh ↑ 8.0 Wh

같은 1 Wh 라도 어디서 소모되느냐에 따라 비용 기여가 달라졌다. 배터리에서 빠지는 1 Wh 는 어디서 쓰든 1 Wh 인데도 그랬다.

실제 영향

medium_open 에서 총 52.9 Wh 쓰는 하이브리드 경로가 14.1 Wh 쓰는 밟고넘기 경로를 이기고 '최적'으로 뽑혔다. E_switch 40.2 Wh 가 비용에 1.005 밖에 기여하지 못했기 때문이다. 에너지 효율 경로를 찾는다는 연구 목적과 정면으로 어긋난다.

수정

현재 식 (정규화 형태) C = wE·(E_motion + E_switch)/E_ref + wS·n_switch + wT·T/T_ref

등가 형태 (논문용) C = α·(E_motion + E_switch) + β·n_switch + γ·T
α = wE/E_ref = 1.0 β = wS = 0.2 γ = wT/T_ref = 0.09

에너지는 에너지끼리 같은 참조값으로 정규화하고, 전환은 횟수 페널티로 분리했다. 전환에는 Wh 로 환산되지 않는 비용이 있기 때문이다 — 착륙 실패 위험, 자세 재수립, 제어 복잡도. n_switch 는 이·착륙을 각각 세므로 비행 한 구간이면 2·wS 가 붙는다.

회귀 방지 테스트를 C++ 쪽에 넣었다 — SwitchEnergyCostsSameAsMotionEnergy: 같은 1 Wh 는 주행이든 전환이든 같은 비용이어야 한다.

03등반 에너지는 위치에너지로 모델링할 수 없다

위치에너지만 쓰면 밟고넘기가 항상 이겨 비교 자체가 무의미해진다. 실제 등반은 모터 토크 급증·슬립·저속 주행 때문에 훨씬 크다. 그래서 climb_mode.energy_per_height_m 를 미지수로 두고 sweep 했다. 실측값이 나오면 곡선 위에 점 하나만 찍으면 된다.

부과 방식

비용은 상승분 Δh 에만 부과한다. 목적지 높이에 비례해 매기면 장애물 위를 여러 셀 지나갈 때 중복 계상된다. 올라갈 때 한 번, 위에서는 평지와 동일, 내려올 때는 공짜 — 위치에너지와 같은 경로 무관(path-independent) 구조가 된다.

04결함 2 — 스무딩이 순위를 뒤집고 있었다

sweep 결과에 논리적으로 불가능한 행이 있었다. 상위집합인 밟고넘기가 우회보다 최대 4.84% 비쌌다 — 90행 중 14행.

단계를 분리해 어디서 뒤집히는지 확인했다.

A* 격자해는 전부 정상이고, 역전은 스무딩에서만 생긴다. 우회 경로는 5.0~5.8% 개선되는데 밟고넘기 경로는 0.4~2.4% 밖에 개선되지 않는다. 밟고넘기 경로는 장애물을 가로질러 이미 짧아 shortcut 여지가 적고, 우회 경로는 길고 지그재그라 개선 폭이 크다. shortcut smoothing 이 그리디 휴리스틱이라 최적을 보장하지 않기 때문이다.

수정

모든 파라미터 지점에서 얻은 경로를 한데 모아, 각 지점마다 전부 재평가하고 최소를 취한다. 후보 집합이 파라미터와 무관하게 같아지므로 단조성이 보장된다.

결과 조작이 아니다 — 후보 경로는 전부 실제 실행 가능하며, 최적 플래너라면 당연히 그중 가장 싼 것을 골랐을 경로들이다. 수정 후 단조성 위반 0건 / 상위집합 위반 0건.

남은 한계

근본 원인(스무더가 비최적)은 그대로다. 이 보정은 modal 간·파라미터 간 비교만 바로잡을 뿐, 같은 조건 안에서 스무딩이 놓친 개선은 못 찾는다. 논문에는 경로 후처리로 shortcut smoothing 을 쓰며 최적은 아니다를 명시하는 편이 정직하다.

읽는 법

하이브리드 비용이 우회와 소수점까지 같다 — 비행을 한 번도 쓰지 않았다는 뜻이다. 하이브리드는 밟고넘기를 못 하므로 우회 아니면 비행인데, 비행이 이득이 안 되니 우회와 같은 경로로 수렴한다.

해석 시 주의

이 결과는 등반계수 2.0 Wh/m 라는 미검증 추정치에 의존한다. INA226 실측이 이 값보다 훨씬 크면 밟고넘기의 우위가 줄고 판도가 바뀐다. 5절 표에서 실측값에 해당하는 행을 보면 된다.

동률 5건은 전부 wE=0, wS=1.0, wT=0 — 에너지와 시간을 완전히 무시해 지상 경로가 모두 비용 0 이 되는 축퇴 조합이다. 승리로 집계하지 않았다.

07C++ 플래너는 장애물을 넘지 못했다 — 재현, 수정, 검증

C++ 3D 상태공간이 지형 추종 고도(airZ = 지형높이 + flight_clearance)를 쓰는데, 이는 상승각 제약과 충돌한다.

격자 0.05 m · 최대상승각 45° 한 스텝 최대 고도변화 0.050 m
0.60 m 장애물 경계에서 필요한 고도변화 0.600 m → 거부

하이브리드 플래너가 어떤 장애물도 날아서 넘지 못했다. 이륙은 되지만 장애물 경계에서 모든 공중 전이가 거부되어 실질적으로 우회와 같아진다.

1 · 결함을 코드로 재현

고치기 전에 먼저 테스트를 썼다. 진단이 틀렸을 가능성을 걸러내기 위해서다. 대조군(RoverClimbCrossesObstacleOnGround)이 통과하므로 도달성 검사 자체는 멀쩡하고 하이브리드만 못 건넌다는 게 확인된다.

2 · 수정 — 비행 구간 고도 고정

Python 에서 했던 것과 같은 구조로 바꿨다.

  • State 에 level(비행 고도 인덱스) 추가
  • buildAirLevels() — costmap 을 훑어 후보 고도 열거 (지형높이 + flight_clearance)
  • 이륙 시 고도 선택, 비행 중 고정, 착륙 시 하강
  • 공중 이동에서 수직 비용·상승각 검사 제거 (고도가 안 변하므로)

같이 걸린 것 둘도 고쳤다.

  • groundSegmentCost() — 스무딩 직선이 장애물 위를 지날 때 등반 비용을 반영한다. 없으면 밟고넘기가 공짜가 된다.
  • buildSwitchPlan() — 비행 구간 에너지를 airMoveHorizontal(dist, 고도) 로 재계산하던 것을 실제 구간 비용 누적으로 교체. 두 번째 인자는 '고도'가 아니라 '지형 상단으로부터의 여유'라 의미가 달랐다.

테스트를 새 API 에 맞추면서 함께 고쳤으므로, 테스트가 느슨해져서 통과할 가능성이 있었다. 확인하려고 이륙 고도를 가장 낮은 하나로 제한하는 개악을 일시 적용했더니 ChoosesHigherAltitudeWhenLowestIsNotEnough 가 다시 실패했다. 테스트가 로직을 실제로 붙잡고 있다는 뜻이다. 개악은 되돌렸다.

Python↔C++ 고도 후보 규칙도 대조했다 — 평지+0.60m 맵은 양쪽 다 [0.80, 1.40], 평지+0.90m 맵은 양쪽 다 [0.80, 1.70].

작업 중 낸 내 실수

처음 쓴 BFS 헬퍼가 방문 집합 키에서 level 을 빠뜨렸다. 같은 셀의 다른 고도가 이미 방문한 것으로 처리되어, 코드는 멀쩡한데 테스트가 실패했다. 0.60m 장애물은 가장 낮은 고도로도 넘어져서 이 실수가 드러나지 않았고, 0.90m 케이스를 추가하고 나서야 잡혔다.

남은 것

  • 등반계수 실측 — INA226 4채널. 지금 결론 전체가 이 값에 걸려 있다.
  • 스무더 비최적 — 경로 풀링은 비교만 바로잡을 뿐 근본 해결이 아니다.
  • 실험 기록 구조 — logging_config.yaml 의 baseline 목록이 플래너 축(smac2d / drone_only / …)이라 modal 축과 어긋난다. trial_summary 에 modal 컬럼도 없다.
  • ground effect 미발동 — flight_clearance 0.8 > activation_height 0.5 라 3D 에서는 영원히 안 켜진다.
  • Gazebo 재확인 — 이제 비행이 가능해졌으니 실제 경로에 이착륙이 나오는지 다시 봐야 한다.
